# Tiered CI Architecture

Bingo adopts a tiered CI architecture that separates standard validation, selective user-facing verification, branch diagnostics, distribution validation, and release publication. This preserves full MPI-enabled tests on Python 3.13 and 3.14 for every pull request while keeping slower or externally visible work out of the ordinary feedback path.

Standard validation runs for every pull request and updates to `main` or `develop`; Python 3.13 produces GitHub-native coverage artifacts and a job summary, and Python 3.14 runs the full suite without coverage instrumentation. Documentation and examples run selectively for relevant changes and for updates to those branches; performance benchmarks and distribution validation run only after updates to `main` and `develop`, or by manual dispatch.

Release publication, signing, and GitHub-release creation are permitted only for exact numeric `X.Y.Z` production tags or `X.Y.ZrcN` release-candidate tags after full-suite validation of a clean installed artifact. The built distribution version must exactly match the triggering tag. Bingo publishes an sdist and Linux x86_64 wheels for Python 3.11 through 3.14, smoke-tests each wheel and the sdist on Python 3.13, and runs the full installed-artifact suite for Python 3.13 and 3.14 wheels. Pushing an eligible tag is the sole publication authorization; no manual environment approval is required. Release candidates publish to PyPI and create signed GitHub prereleases even when their tagged commit is on `develop`; production tags create stable GitHub Releases. Shared environment preparation is owned by a local composite action, workflows retain event and permission policy, obsolete PR and branch runs are cancelled, and validation workflows remain read-only.
